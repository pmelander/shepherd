# Design: Bruno — a Herdr desk companion on M5Stack Core Basic

Related, not superseded: `shepherd-cardputer-herdr-remote.md` (BUILT). Bruno is a
second client for the relay that design produced. Read its `## Implementation
Notes` before starting — several of its claims were falsified by hardware, and
the same class of mistake is available here.

## Problem Statement

Five Claude Code agents run across five Herdr workspaces on one workstation.
Shepherd solved *answering* a blocked agent from across the room. It did not
solve the ordinary case: an agent finishes while you are looking at a different
workspace, and nothing on the desk tells you. Herdr reports `done` for exactly
this ("finished, and you have not looked yet"), and until now nothing consumed
it except a device in a pocket.

Bruno is a wired desk companion that watches the herd and reacts. It is a
second screen, not a remote: it never touches Herdr.

## What Makes This Cool

**Bruno speaks the agent's actual words.** The relay already extracts what an
agent last said — `recap.py`, shipped, and hardened against three real failure
modes on live panes (tool calls wearing the same bullet as messages, tables
reflowing into noise, Claude Code's own recap chrome). So when an agent
finishes, Bruno can put *its sentence* in a speech bubble:

```
┌──────────────────────────────┐
│  ╭────────────────────────╮  │
│  │ elasmigr finished:     │  │
│  │ "PR #75587 open, your  │  │
│  │  review next"          │  │
│  ╰──────────┬─────────────╯  │
│   ( ^ o ^ ) │                │
│    /|   |\                   │
└──────────────────────────────┘
```

Nobody would guess that from the brief, and it costs almost nothing: the hard
part is already written and already tested against real terminals.

The second cool thing is structural. Approach C makes the relay *publish* its
frame stream, so Bruno is the first subscriber rather than a special case. For
an open-source project the stream is arguably the product — the same tee feeds a
menu-bar app, a web page, or somebody else's board, without the relay learning
about any of them.

## Constraints

- **Watch-only.** One-way link. The relay writes; nothing reads back. No action
  gate, no HMAC, no decision ids, no audit log, no input path to reason about.
- **No BLE — but not by deleting a file.** `main.cpp` and `data.h` make **16
  calls** to `bleInit`, `bleWrite`, `bleConnected`, `bleAvailable`, `bleRead`
  and friends, and **not one of them sits inside a board guard** (14 in
  `main.cpp`, 2 in `data.h`, 0 guarded). Dropping `ble_bridge.cpp` from the
  build gives undefined references, not a clean no-BLE build. See the firmware
  section for what to do instead.

  This document first said 15, from a script that counted *lines containing a
  call* rather than calls — line 841 carries two
  (`!bleConnected() ? "-" : bleSecure() ? ...`). Recorded rather than quietly
  corrected, because a document whose whole method is "probe, do not reason"
  has no business citing a checkable number it got wrong.
- **No keyboard.** The Core Basic has three buttons and Bruno uses none of
  them. Every Shepherd mechanism that keys off a keypress needs a different
  rule here (see Open Questions).
- **Hardware unverified**, and one unknown outranks the rest: **does `Serial`
  on this board actually reach the USB connector?** Bruno has no BLE, so if the
  answer is no, Bruno has no fallback and no way to say so. This project has
  already been bitten by precisely this: the Cardputer ADV's board definition
  sets `ARDUINO_USB_MODE=1` without `ARDUINO_USB_CDC_ON_BOOT`, routing `Serial`
  to an unwired UART0 while ESP-IDF logs still reached the host — an asymmetry
  that cost three wrong hypotheses in one session. Core Basic is a different
  family (classic ESP32 behind an external USB-UART bridge, not the S3's native
  USB), so the specific trap will differ, which is exactly why it must be
  probed rather than reasoned about. This is bench probe #1, before any Bruno
  code is written.
- Display driver, button behaviour, speaker, and whether v2.7 carries an IMU are
  likewise assumptions until the board arrives. `-DBOARD_HAS_PSRAM` was taken
  from a spec sheet once here and falsified by esptool on the actual chip.
  Nothing board-specific gets asserted in this document.
- **Open source.** A stranger must be able to get this running. That makes
  distribution a design constraint rather than an afterthought, and it surfaces
  a blocker the relay already has (see Distribution Plan).

## Premises

All six confirmed in session.

1. **Bruno is upstream's own product, re-pointed.** `claude-desktop-buddy` is a
   desk pet driven by a desktop app over serial. The vendored fork already
   routes `Serial` into Shepherd's handler: `_usbLine.feed(Serial, out)` →
   `_applyJson()` → `shepherdUiApply(line)`. Bruno is not a new device class.
2. **A second transport, not a second protocol.** `Transport` is already a
   Protocol with BLE and Fake implementations. Frames stay as they are; Bruno
   ignores the fields it does not use (`o`, `w`, `r`, `x`).
3. **One source of frames.** The relay takes a singleton lock deliberately, so
   two relays cannot fight over one device. Bruno must therefore consume the
   existing relay's output rather than poll Herdr itself.
4. **Bruno inherits a bug on day one.** `_usbLine` is still `_LineBuf<1024>`
   while frames reach ~1.4KB with option blocks. That is the same silent
   truncation fixed on `_btLine` and never fixed on the serial side. It presents
   as a screen that simply stops updating.
5. **Speaking needs a push, not a fetch.** Shepherd pulls an answer on a
   keypress. Bruno has no input, so the relay must push the answer when an agent
   finishes. That is a change to the push loop.
6. **Hardware claims stay marked as assumptions** until the board is in hand.

## Approaches Considered

**A — Fan out transports inside the one relay.** `Runner` holds a list of
transports and writes each frame to all of them. Ruled out in session: it puts
the change inside the loop Shepherd depends on, for a coupling Bruno does not
need.

**B — A second read-only relay process.** Ruled out in session: two `herdr
agent list` pollers against one Herdr, and a duplicated push loop that drifts
the first time either side changes.

**C — Publish the frame stream; Bruno subscribes.** Chosen.

## Recommended Approach

**C. The relay tees every frame it sends to a local NDJSON file. A small
`bruno.py` follows that file and writes each line to the serial port. Bruno
never talks to Herdr, and the relay never learns Bruno exists.**

### The stream

- One frame per line, exactly the bytes already sent to Shepherd, appended to
  `$HERDR_PLUGIN_STATE_DIR/frames.ndjson`.
- Append-only. A latest-frame-only file was considered and rejected: Bruno must
  notice a `blocked` → `done` transition, and a poller can miss one that happens
  between polls. Appending lets a subscriber read every frame actually sent.
- **Rotation is rename-and-reopen, not truncate-in-place**, and the difference
  matters: a follower tracking a byte offset silently duplicates lines after a
  truncate and silently skips them after a rename it did not notice. So the
  relay renames to `frames.ndjson.1` and opens a fresh file at a small cap, and
  `bruno.py` detects the swap by watching for the file shrinking or its identity
  changing, then reopens from the start.
- Written unconditionally. A file nobody reads costs nothing, and making the tee
  conditional on a subscriber existing means a subscriber that starts late sees
  nothing.
- The tee is additive: it does not change what the relay sends, when, or to
  whom. If it fails, it fails alone — wrap the write broadly enough that a full
  disk cannot take Shepherd down. The audit log already sets this precedent, and
  for the same reason: it catches `Exception`, not `OSError`, because a path
  with a null byte raises `ValueError` from `mkdir`.
- **This makes the frame stream a public interface** (see Open Questions 2 —
  shipping `bruno.py` to strangers decides it, so the doc stops pretending
  otherwise). The frame's existing `v` field is that contract's version.

### The subscriber

`plugin/bruno.py`, roughly:

- follow `frames.ndjson` from the end, like `tail -f`
- open the serial port **with DTR and RTS deasserted before `open()`** — on
  these boards DTR is the auto-reset line, and `serial.Serial("COM5", …)`
  reboots the device the moment you look at it. This cost a full misdiagnosis
  on Shepherd (it presented as BLE instability); see the warning beside
  `SHEPHERD_SERIAL_PROBE` in `firmware/platformio.ini`.
- write each line, never read
- reconnect when the port disappears, because the board will be unplugged

### The push-on-completion change — additive, and NOT a version bump

Add `m` to a row — for message: the agent's last answer, populated when it
transitions to
`done`, fetched once and cached against `state_change_seq` exactly as blocking
prompts already are — **including the pop**. `runner.py` drops a cached prompt
the moment an agent leaves `BLOCKED`; `m` must be dropped the moment an agent
leaves `done`, or a stale sentence rides along on a later `working` row.

Short: the speech bubble is about three lines of thirty characters, so
`truncate_body(text, limit=120)` — the limit is already a parameter, no new
constant needed.

**`m`, not `b`.** `b` already means something else on the wire: the ~900-char
detail body on a `deet` frame, fetched on request. Frame types are disjoint so
a parser would never confuse them, but this stream is now a public contract
(Open Question 2), and a public protocol that spends the same letter on two
meanings is how the next person misreads it. Every other key in the format —
`q`, `o`, `w`, `x`, `d`, `r` — means one thing.

**`PROTOCOL_VERSION` does not move.** This is the correction to the first draft
of this document, which called it v4 and then claimed in the same breath that
Shepherd stays untouched. Those cannot both be true: the device *refuses* a
version it does not recognise and says so on screen, so bumping 3→4 would black
out the Cardputer in your pocket the moment the relay upgraded, until reflashed.

A bump is only owed when both sides must move together — v3 earned one because
it changed the signed message's shape. `m` earns none: the device parser reads
the keys it knows and ignores the rest, so an added field is invisible to
firmware that does not want it. Shepherd genuinely stays untouched, and gains
the option of showing the same sentence later without a keypress.

### The firmware

- New PlatformIO env, `bruno-core`, targeting the Core Basic.
- **`ble_stub.cpp` rather than an exclusion.** `build_src_filter` swaps
  `ble_bridge.cpp` out and a stub in, implementing the same nine functions as
  no-ops (`bleConnected()` returns false, `bleAvailable()` returns 0, and so
  on). This is the small fix: the alternative is threading `#ifdef` guards
  through 15 call sites in code Shepherd depends on, to achieve the same
  linkage.
- **`main.cpp` is not board-modular and this is the real cost.** It already
  carries 20 `CARDPUTER_ADV` conditional sites governing buttons, keyboard,
  display geometry and power. A third board wants a third branch at most of
  them. Two honest options, and this document does not pretend the first is
  free: add the third branch (fast, and makes the file worse), or move the
  board-conditional parts behind `hal.h` where the other two already went
  (slower, and is what `hal.h` exists for). Decide at implementation time with
  the board in hand, and expect this to dominate the firmware effort — not
  `bruno_ui.cpp`.
- Reuses `shepherd_frame.h` unchanged, so the native suite covers Bruno's
  parsing for free.
- Fixes `_usbLine` to 4096 (premise 4) before anything else.
- New `bruno_ui.cpp`: one avatar, one speech bubble, at 320×240.
- Bruno's states map to what the relay already reports: `working` → busy,
  `blocked` → attention **with the prompt `q` in the bubble** (Bruno cannot
  answer it, but "elasmigr is asking about a force-push" is exactly the thing
  worth turning your head for), `done` → celebrate with `m`, all idle →
  potter. Bruno ignores `o`, `w`, `r` and `x` — the fields that exist only so a
  device can act.

## Open Questions

1. **How does Bruno stop celebrating?** Shepherd clears attention on a
   keypress, and getting that wrong cost two iterations — marking a
   notification "seen" because the screen was lit meant the alarm's own
   wake-up satisfied it. Bruno has no keys, so a timer is the only signal
   available. That makes time the right answer here for the same reason it was
   the wrong answer there. Duration needs living with, not deciding now.
2. ~~Is the frame stream public or internal?~~ **Resolved: public.** Shipping
   `bruno.py` to strangers via the plugin channel decides it, and leaving the
   question open while already executing the "public" branch was a soft lie.
   The consequence is a commitment: the frame's `v` field is now a contract
   other people's clients depend on, and additive fields stay additive.
3. **Does Bruno need the relay running to be useful?** No relay means no frames
   means a stale screen. Bruno must say so rather than showing a contented pet
   over a herd it cannot see — Shepherd's `NO SIGNAL` rule, ported. With no
   BLE and no keys, staleness is the only failure Bruno can report, so it has
   to report it well.
4. **Hardware:** display driver, button behaviour, speaker, IMU on v2.7 — and
   `Serial`-to-USB, which is bench probe #1 and the one with no fallback.
5. **Relay platform support.** See below; this one blocks the stated goal.
6. ~~How does `bruno.py` get launched without punishing Shepherd users who
   have no Bruno?~~ **Decided, because leaving it open left the original
   hazard in the plan.** `bruno.py` gets its own `[[startup]]` entry in
   `herdr-plugin.toml`, and its first act is to look for a port in
   `$HERDR_PLUGIN_CONFIG_DIR/bruno.port`. No file, no Bruno: log one line and
   exit 0. An install with no Bruno hardware therefore costs exactly one
   process start per Herdr session and nothing after it — no retry loop, no
   log noise, no held port. Creating that one file is the whole opt-in, which
   also means Bruno can be turned off by deleting it. Implemented in Next Steps
   4b.

## Distribution Plan

The goal is other Herdr users, so this is load-bearing.

- **Firmware:** `scripts/merge_bin.py` already produces a single flashable
  image. Add a `bruno-core-merged.bin` and attach both to a GitHub release, so
  a stranger flashes with `esptool` or M5Burner and needs no toolchain.
- **Relay + subscriber:** Herdr installs plugins from a repo subdirectory —
  `herdr plugin install pmelander/shepherd/plugin`. That channel already exists
  and needs no new infrastructure.
- **Blocker, and it is a real one:** `plugin/herdr-plugin.toml` declares
  `platforms = ["windows"]`, honestly, because the command array is `py -3`.
  Every non-Windows Herdr user is excluded today. Shipping Bruno as open source
  means either making the interpreter invocation portable or documenting the
  limitation prominently. This was not a problem while the audience was one
  laptop.

## Success Criteria

- Bruno sits on the desk for a week without a reboot, a stale screen, or a
  hand-restart.
- An agent finishing produces a visible celebration and its own words within a
  couple of seconds.
- A stranger flashes a prebuilt image, runs one `herdr plugin install`, and gets
  a working Bruno without a compiler.
- **Shepherd keeps working without being reflashed, and its tests stay green.**
  Stated this way on purpose: the first draft claimed "untouched ... true by
  construction" while also bumping the protocol version, which would have
  blacked out the Cardputer until reflashed. Additive-only is what makes the
  claim true, and it is a constraint on the implementation rather than a
  property of the architecture.

## Next Steps

1. Fix `_usbLine` to 4096. Do this first and separately: it is a bug in shipped
   code, on the serial path Shepherd does not use and its tests do not cover,
   and it is worth a commit of its own regardless of whether Bruno happens.
2. Add the tee to the relay: guarded write, rename-and-reopen rotation. Small,
   additive, testable against the existing fakes with no hardware.
3. Add `m` with push-on-completion and **no version bump**, cached against
   `state_change_seq` and popped when the agent leaves `done`. Tests for both
   halves of that cache — a per-tick `herdr agent read` would spawn a process a
   second, and a missing pop puts a stale sentence on a working agent.
4. Write `plugin/bruno.py` against a **hand-written frames file**, no board
   attached. Deassert DTR and RTS before `open()`. This step is fully testable
   today and should be finished before the hardware arrives.
4b. Wire the opt-in: a second `[[startup]]` entry for `bruno.py`, and the
   `bruno.port` check that makes it exit 0 on an install without hardware.
   Test it by running with no port file present and confirming one log line and
   no lingering process — a Shepherd user who never buys a Core must not
   notice Bruno exists.
5. **When the board lands, probe before you code.** In order: does `Serial`
   reach USB at all (the one with no fallback); `esptool flash_id` for the real
   chip and flash size; then buttons, speaker, IMU. Record what the board
   actually reports in `VENDOR.md`, not what the product page claims.
6. Decide the `main.cpp` question with the board in hand: third `#ifdef` branch,
   or move the board-conditional parts behind `hal.h`. Expect this to dominate
   the firmware effort.
7. Then `bruno_ui.cpp`.
8. Before release: the `platforms = ["windows"]` blocker, or the open-source
   goal is not met.

## What I noticed about how you think

- You named the genre before the features: *"It's more tamagochi than remote."*
  That one clause ruled out three of the four screen designs before I offered
  them, and it is why the speech bubble is a bubble rather than a status bar.
- You overrode my recommendation three times out of five, and every override
  went the same direction: **less capability, more generality.** You took
  watch-only over focus-only, and publishing the stream over wiring the
  transports together. That is a coherent taste, not indecision — you keep
  choosing the smaller surface and the more general interface.
- *"drop the names, it wont work when we have like 10 agents"* — you designed
  the strip for a herd you do not have yet, and rejected the version that only
  works at your current size.
- *"I don't understand, when I unplug the device from Serial and Reboot it
  should connect by BLE"* — you reason from what the system promised rather
  than from what it did. That sentence is what found a relay that had outlived
  its Herdr by two days.
