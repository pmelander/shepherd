## Problem Statement

Five Claude Code agents run concurrently across five Herdr workspaces
(`new-pricemanager-client`, `infrastructure-work`, `tempo-curve-adjustment`,
`elastic-migration`, `herdr-remote` — verified live via `herdr api snapshot` on this
host). When one stops and waits for a human, nothing physical notices. An agent can sit
blocked for minutes while attention is elsewhere, and finding out means alt-tabbing
through workspaces.

The device is a **pocket herd radio**: a battery-powered object that shows all five
agent states at a glance, chirps when one blocks, and lets the block be answered
without touching the laptop.

### The event naming rule (verified on this host — protocol 20)

Three different surfaces, three different spellings. Getting this wrong produces a
silent false negative, so it is stated before anything else:

| Surface | Field | Spelling |
|---|---|---|
| `events.subscribe` | `params.subscriptions[].type` | **dotted** — `pane.agent_status_changed` |
| `events.wait` | `params.match_event.event` | **underscored** — `pane_agent_status_changed` |
| the emitted event | `type` const | **underscored** — `pane_agent_status_changed` |

Confirmed by enumerating the `Subscription` and `EventMatch` `oneOf` lists in
`herdr api schema`. The emitted event carries `agent_status`
(`idle`|`working`|`blocked`|`done`|`unknown`), `pane_id` and `workspace_id`.

**Whether it fires on rule-derived transitions is unresolved.** `herdr-assist`'s bridge
header states that on Herdr **0.8.0** it is not emitted for these transitions
("verificado ao vivo") and falls back to a 1 Hz `pane.list` reconcile.
`lfsmoura/led-agent-status` reacts to that event on Herdr >= 0.8.0. This host is 0.8.2
and its schema defines it. **This matters for Approach B, not for the chosen Approach A**
— A inherits a bridge that polls on Windows regardless. Every latency figure below is
therefore stated against *the bridge observing* the transition.

## What Makes This Cool

The narrowed, verified novelty — after finding dense prior art:

- **Per-agent state over BLE does not exist.** Anthropic's `claude-desktop-buddy` wire
  protocol is structurally aggregate-only: `total`, `running`, `waiting`, `msg`,
  `entries`, `tokens`, `tokens_today`, and `prompt` as a **single object** (`id`/`tool`/
  `hint`), not an array — verified against `REFERENCE.md`. It cannot express "which of my
  five" or two simultaneous blocks. Every BLE buddy firmware renders those fields.
- **No *per-agent, screen-bearing, battery-powered* BLE device speaks Herdr.** Narrowed
  from an earlier, falsified claim: `lfsmoura/led-agent-status` *is* a Herdr plugin
  acting as BLE central to an LED strip, so "no BLE device speaks Herdr" was wrong. It
  carries no per-agent state and no screen — and it is a working precedent for the
  BLE-central-inside-a-plugin pattern Approach B wants.
- **Nothing here is pocketable.** `walcew/herdr-assist` is a mains-adjacent desk panel
  with a router dependency. `0cv/herdr-mobile-relay` and `AltanS/collie` are phones.
  Battery-first, no-network, radio-bonded is unoccupied.
- **The ADV's peripherals are untouched by anyone**: ES8311 codec, MEMS mic, BMI270 IMU,
  and BLE link RSSI as a proximity signal.

Explicitly NOT novel, claimed as such earlier in this session and retracted: "nobody
built a physical multi-agent Herdr panel." `walcew/herdr-assist` did, with a bell and a
Cardputer port. The status strip is a layout choice on a data model that ships today.

## Constraints

Checked on this host unless marked otherwise.

- **Herdr's socket API is local IPC only.** On Windows the transport is a named pipe
  named after its own path (`\\.\pipe\C:\Users\6874\AppData\Roaming\herdr\herdr.sock`,
  confirmed by enumerating `\\.\pipe\`). The `.sock` *file* holds
  `pid:start_time_nanos` as a liveness stamp, not an address — port 1256 is not
  listening. A host-side bridge is mandatory.
- **The API has no authentication.** Protocol 20, ~80 methods; grepping the 265KB schema
  for nonce/token/handshake/auth finds only theme colour tokens and
  `pane.clear_agent_authority`. Local-trust by design, and it exposes `pane.run` and
  `pane.send_keys`.
- **Display: 240x135 on a 1.14" panel = a 40x16 physical text grid at 6x8.**
- **The pane viewport lock is a parameter, not a constant.** herdr-assist locks a session
  via `herdr terminal session control <pane_id> --cols N --rows M` — whatever the client
  asks for. Its README documents a 220x48 grid and a 42x18 panel fit, so the "14 rows"
  figure from an earlier draft was one build's number, not a property.
- **6x8 glyphs are not legible at 1m, by arithmetic.** 275px diagonal over 28.96mm =
  0.105 mm/px, so an 8px cell is 0.84mm; 20/20 acuity resolves ~5 arcmin ≈ 1.45mm at 1m.
  Most 6x8 fonts ink 7 of 8 rows, so 2x is marginal. **The strip renders at 3x** — spec
  the scale factor, not a millimetre figure.
- **ESP32-S3 has no Bluetooth Classic** — BLE 5 only, no SPP.
- **The WinRT BLE backend cannot request an ATT MTU.** `bleak` exposes `mtu_size`
  read-only off `self._session.max_pdu_size`, and only after a GATT session exists.
  Read it after connect; floor to 20 bytes if absent.
- **`bleak` on Windows cannot perform a passkey ceremony.**
  `bleak/backends/winrt/client.py` line 523 comments "Currently only supporting Just
  Works solutions...", line 524 hardcodes `ceremony = DevicePairingKinds.CONFIRM_ONLY`,
  and the `PairingRequested` handler calls `args.accept()` unconditionally. Verified in
  source. Consequence: the peripheral must advertise IO capability
  **`NO_INPUT_OUTPUT` with MITM off**, or CONFIRM_ONLY pairing fails outright.
- **No PSRAM on the S3FN8.** herdr-assist's Cardputer build uses **cJSON from the IDF**,
  not ArduinoJson. **Its buffer constants must be re-read from `cardputer/platformio.ini`
  before use** — the README documents a 12KB `HERDR_CONTENT_LEN` and a 220x48 grid, which
  does not match figures quoted in an earlier draft. Inherit whatever the file says.
- **NimBLE-Arduino version trap.** The build is pioarduino 55.03.311 (Arduino core 3.x /
  IDF 5.5), which needs NimBLE-Arduino **2.x**. Nearly every NUS + bonding example in
  circulation is the incompatible 1.4.x API. This is the largest single unknown in the
  firmware step. Also: **NimBLE stores bonds in NVS**, which collides with the WiFi
  credential erase (see Security).
- **This host has no embedded toolchain**: no PlatformIO, arduino-cli, ESP-IDF, esptool.
  Installing it is an explicit step, not a footnote.
- **Flashing an S3 over native USB needs the physical BtnG0+BtnRST download-mode
  sequence** — there is no software path. And **Cardputer and Cardputer-Adv share a USB
  VID**, so nothing autodetects which board is attached.
- **This host has no Rust.** Available: Python 3.12.10, Node 24.15, Bun, .NET 10.0.400,
  Go. `bleak` is the least-friction central; **.NET/WinRT is the only path to an
  in-product passkey**. Avoid Node `noble` on Windows.
- **Corporate context.** This laptop holds five NLTG source panes. An unmanaged ESP32 on
  the corporate WLAN holding a token that can drive agent input against work repos is not
  acceptable. Leading reason BLE beats WiFi, ahead of power. **This constrains the
  Saturday WiFi spike too** — see Security.

## Premises

1. **The device is a pager AND a herd glance.** (Revised in session; the original claimed
   it should not notify because Collie already does. Rejected by the user.) Overlap with
   Collie is deliberate: always-on, always-visible, no unlock, five agents at once.
2. **The bridge is forkable; the firmware and transport are the novel work.** (Revised in
   session — originally stated backwards.) `herdr-assist/plugin/herdr_bridge.py` is
   pure-stdlib Python, a real `herdr-plugin.toml`, runs on Windows from plugin 0.5.0,
   listens on TCP 9375 with UDP discovery, and carries per-agent state with per-pane
   targeting. **On Windows it polls rather than subscribing** —
   `USE_CLI = os.name == "nt"` selects a poll loop over the event loop, per its own
   README. Forkability survives; any latency argument resting on push does not.
3. **Read herdr-assist before writing BLE code**, and take its constants from source
   rather than its README.
4. **`m5-onboard` is not the toolchain shortcut an earlier draft assumed.** It detects
   the device over USB, flashes **UIFlow 2.0**, and pushes a **MicroPython** bundle to
   `/flash/`. It does not build or flash Arduino/PlatformIO C++ and does not remove the
   manual PlatformIO install. Running it before the firmware step would **overwrite the
   device with UIFlow**, which the next step then has to replace. Its own docs also say
   the ADV cannot be distinguished from the v1 before UIFlow is flashed, so it cannot
   validate the ADV assumption either. Demoted to an optional USB smoke test.
5. **`shepherd` is free within the `herdr-plugin` topic, not globally.**
   `rahlk/Shepherd`, `floren/shepherd`, `roderik/shepherd` and
   `joelhooks/pi-shepherd` exist. `dcolinmorgan/herdr-remote` and
   `walcew/herdr-assist` are taken, so the local directory name collides too.

## Approaches Considered

### Approach A: Fork and Flip (CHOSEN)
Keep `herdr-assist`'s plugin as the Herdr-facing half. Add a `bleak` relay that connects
to its TCP port and re-frames each line into a per-agent BLE payload. Firmware is its
`cardputer/` build with the WiFi/TCP client removed and NimBLE-Arduino 2.x advertising
NUS. Effort M (human ~2 weekends / CC ~5 hours). Risk Med.

### Approach B: Shepherd proper
One `herdr-plugin.toml` package that speaks the socket API directly via `HERDR_BIN_PATH`
and is itself the BLE central — the pattern `lfsmoura/led-agent-status` proves. Own
per-agent wire format. Marketplace-publishable, Herdr-managed lifecycle and logs.
Effort L (human ~3-4 weekends / CC ~8 hours). Risk Med.
Not chosen: rewrites the layer that can be forked, slowest to the moment that proves the
idea. Remains the refactor target once the frame schema is settled — and the only route
to an in-product passkey, since a .NET/WinRT central belongs there. **The event probe is
a decision input for this approach**, not for A.

### Approach C: Pocket herd radio
B's plumbing with the product bet off the screen: per-agent earcons on the ES8311,
push-to-talk into agent input via the MEMS mic, RSSI-routed notification.
Effort XL (human ~6+ weekends / CC ~12 hours). Risk High.
Not chosen as a starting point: three hard subsystems at once. Earcons are additive later.

## Recommended Approach

**Approach A**, over two weekends. The WiFi build flashed first is not a fallback — the
firmware step removes its transport — it is a **risk-retirement spike** doing two jobs:
proving the ADV boots someone else's v1/v1.1 firmware, and showing what the per-agent
payload should contain before any of it is designed.

### Wire protocol (the artifact Approach B inherits)

Newline-delimited UTF-8 JSON over NUS. **Accumulate bytes until `\n` before decoding** —
multi-byte UTF-8 will straddle chunk boundaries. Chunk to `mtu_size - 3`, read after
connect, floor 20.

**Host → device snapshot.** Emitted on change and **at least every 10s** as a keepalive,
so a quiet herd never false-triggers the staleness marker:

```json
{"t":"snap","seq":41,"ts":"2026-09-04T11:34:57Z",
 "a":[{"i":"w9:p1","n":"elastic-migration","s":"blocked","e":494,
       "q":"Allow Bash(git push --force origin main)?","r":"req_abc123"},
      {"i":"w2:p1","n":"pricemanager-client","s":"idle","e":720}],
 "n_extra":0}
```

- `i` = `pane_id`, the only join key. Herdr pane ids are already workspace-qualified
  (`w9:p1`), so `workspace_id` is redundant for the join and is not sent.
- `n` = the workspace's `identity_cwd` basename, **host-truncated to 22 chars, head-kept
  with a trailing `~`** (so `new-pricemanager-client` → `new-pricemanager-clie~`).
- `s` = the `AgentStatus` enum verbatim. **The device derives its glyph from `s`** — no
  glyph field, one source of truth.
- `e` = seconds in state at send time. The device extrapolates the live counter from `e`
  plus its own monotonic clock since frame receipt.
- `q`/`r` present only when blocked. `q` is **host-truncated to 100 chars** to fit the
  detail block's ~3 lines of 40 cols. `r` is the decision id to echo back.
- `seq` is per-connection and monotonic. A gap makes the device request a full snapshot;
  a reconnect resets it to 0.
- Hard cap **5 rendered agents**, matching the five strip slots. `n_extra` counts the
  remainder and the strip renders `+N`. Sorted blocked-first, then longest-waiting.

**Device → host action:**

```json
{"t":"act","i":"w9:p1","r":"req_abc123","k":"approve","mac":"<hex>"}
```

`k` is one of a **closed set: `approve` | `deny` | `focus`**. Every action echoes the
`pane_id` it was rendered against, so a snapshot arriving between render and keypress
cannot misroute a decision.

**Device → host status** (device battery lives here, not in `snap` — it is the device's
own reading and nothing on the host knows it):

```json
{"t":"dev","bat":87,"rssi":-58,"fw":"0.1.0"}
```

### Security requirements (non-negotiable)

Herdr's API is unauthenticated and exposes `pane.run` and `pane.send_keys`. A BLE bridge
without app-layer auth is a shell on a laptop holding NLTG source, for anything in range.

- **Encrypted link: Just Works LESC bonding**, peripheral IO capability
  `NO_INPUT_OUTPUT`, MITM off — required to match bleak's `CONFIRM_ONLY`. NUS
  characteristics and the TX CCCD are encrypted-only. Do not ship the link unencrypted.
- **The on-screen passkey is deferred, not dropped.** Two routes back: pair once
  out-of-band via Windows Settings, which does prompt, then let bleak reuse the bond; or
  write the central in .NET/WinRT, which keeps the passkey in-product and belongs to
  Approach B. Note this is a conscious downgrade from `claude-desktop-buddy`'s own
  recommendation (DisplayOnly + 6-digit passkey), which is the main argument for the
  app-layer MAC below.
- **The relay mints and verifies a device token, concretely.** herdr-assist's HMAC
  protects the bridge↔panel TCP hop, which the relay terminates — the BLE hop inherits
  nothing, so "inherit the HMAC" was wrong. Implementation: a 32-byte secret generated at
  relay first run, written to the relay's config with owner-only permissions and flashed
  into the firmware at build time; every `act` frame carries
  `mac = HMAC-SHA256(secret, seq|i|k|r)` and the relay drops any frame whose MAC or `seq`
  fails. This gives `approve`/`deny` one-shot replay protection via `r` and gives `focus`
  freshness via `seq`, which Just Works alone does not.
- **The relay enforces the closed action set on the device→host direction** — the one that
  matters. `approve` | `deny` | `focus` only, mapped onto the bridge's `pane send-text` /
  `pane send-keys` / `agent focus` by `pane_id`. Everything else is dropped and logged:
  raw key passthrough, `C-c`, Tab, free text, and `pane.run` in any form. This is why the
  relay exists rather than a straight TCP-to-BLE pipe — the plugin is unmodified, its
  device protocol is **not** passed through.
- **The Saturday WiFi spike runs on an isolated network, against a throwaway workspace.**
  Phone hotspot or a guest SSID — never the corporate WLAN — and pointed at a scratch
  Herdr workspace, not the five live NLTG ones. The spike is exactly the configuration the
  Corporate Context constraint forbids; isolating it is the condition for running it.
- **Erase WiFi provisioning once, before first bonding.** The spike writes SSID/PSK to
  NVS. **NimBLE also stores bonds in NVS**, so a blanket erase at boot would re-pair
  forever. Erase the WiFi namespace only, one-shot, before the first BLE bond. (An earlier
  draft also claimed a plaintext microSD credential file — **unverified**; herdr-assist's
  README puts credentials in NVS. Confirm in `cardputer/` before treating it as fact.)
- **Restore the pane viewport on release.** Rendering `q` from the snapshot needs no lock,
  so v1 never takes one. If a bounded read is added later, release on read-close, on BLE
  disconnect, on relay `atexit`/SIGTERM, unconditionally on reconnect, and via a
  bridge-side TTL — because relay *death* is not observable by the relay.

## Approved Screen Layout

Chosen from four mockups, then revised for the legibility arithmetic. Top band uses **3x
glyphs (18x24px)** so the glance works at a metre; the detail block stays at 1x 6x8 in
the remaining ~103px (~12 rows of 40 cols).

```
+------------------------------------------+ 240px
|  *    o    *    !    o   +2  4i 1b   87% |  3x glyphs + 1x overflow/counters/battery
|  1    2    3    4    5                   |  1x slot labels
+------------------------------------------+
| 4 elastic-migration          BLOCKED     |  12 rows @ 6x8, 40 cols
| waiting 8m 14s                           |
|                                          |
| Allow Bash(git push --force              |
| origin main)?                            |
|                                          |
| [y] approve         [n] deny             |
| [f] focus on PC     [r] refresh          |
| [1-5] jump                               |
|                               seq 41 ok  |
+------------------------------------------+

  *  idle     o  working     !  BLOCKED
  x  exited   ?  stale (>30s without a snapshot; keepalive is 10s)
```

The top band is the product: at 3x it is legible at a metre, so it answers "does anything
need me?" without the device being picked up. `+N` sits between the glyphs and the
counters. Battery percentage lives there from the `dev` frame because full battery UI is
cut but the criterion needs it observable. `seq` in the corner makes staleness visible.

Rejected: dense all-agents list (unreadable at a glance), one-agent big type (loses the
herd), IMU ambient/pickup two-mode (kept as a later addition). **`[enter] read 20` and
`[p] prompt` were removed** — both are cut from v1 (see Cut list), and an earlier draft
bound keys to features it had also cut.

## Success Criteria

**The acceptance test, weekend two:** five real workspaces running, device in a pocket, a
real `git push` approval prompt answered from the sofa without touching the laptop.

**Weekend one target:** per-agent frames rendering on the strip over BLE, on the bench,
bonded with Just Works.

Secondary, in order:
- **Five of N agent states** visible in one glance with no scrolling, `+N` shown when
  `n_extra > 0`. Strip glyphs at 3x the 6x8 cell.
- Blocked chirp within **2s of the bridge logging the status change** — measured from the
  bridge's log line to the device chirp. The bridge's poll cadence (unknown until its
  source is read) stacks on top of this, so the user-visible latency is 2s + cadence.
  Emitter is a single monotone chirp on the 1W speaker; per-agent earcons are out of scope.
- BLE reconnect after walking out of range and back: automatic, under 10s, backoff capped
  at **3s** so the second reconnect still meets it.
- Zero WiFi credentials on the device — WiFi NVS namespace erased after the spike, BLE
  bond namespace intact.
- No pane left at a **non-default geometry** after a disconnect. (v1 takes no lock at all,
  so this is a regression guard rather than a feature.)
- *Provisional:* a full working day on one charge. Cannot be a criterion until the power
  budget in Open Questions is measured.

   Read the token via `herdr plugin config-dir herdr-assist`.

   (~1400 lines for the bridge). Record the poll cadence, the real buffer constants, and

5. **Optional, 20 minutes: probe the event.** Throwaway script on the named pipe:
   `events.subscribe` with `subscriptions:[{"type":"pane.agent_status_changed"}]`
   (**dotted**), then watch for emitted events whose `type` is
   `pane_agent_status_changed` (**underscored**). Decides whether Approach B can be
   push-driven. Does not gate A.
6. **The relay.** Python 3 + `bleak`. Needs: the `{"t":"hello","token":"..."}` handshake
   (the bridge disconnects after 5s without it), the
   `HMAC-SHA256(token, "nonce|ip|port|name")` discovery signature, the frame reshaping and
   truncation above, runtime chunk sizing off `mtu_size`, the 10s keepalive, the closed
   action filter, MAC verification, and a reconnect loop with a 3s backoff ceiling. Write
   the reconnect loop first — it is most of the perceived quality.
7. **Firmware.** Fork `cardputer/`, keep M5GFX and cJSON and its own buffer constants,
   remove the WiFi/TCP client, add **NimBLE-Arduino 2.x** advertising NUS with Just Works

   panel uses LVGL 8.4; its Cardputer port does not — follow the port). Erase the WiFi NVS
   namespace once, before first bonding.
8. **Weekend two: the acceptance test.**

### Architecture: herdr-assist is not used at all

Step 0 first corrected the *firmware* fork target, then a user challenge dissolved the host side
entirely.

**Firmware forks `y88huang/claude-desktop-buddy-cardputer`**, not herdr-assist. It targets the
Cardputer ADV by name (ESP32-S3 StampS3 + 1.14in 240x135 ST7789 + BMI270 + 56-key matrix +
WS2812B on GPIO 21), builds with `pio run -e cardputer-adv -t upload`, already implements NUS BLE
with keyboard approvals, an audio jingle and an LED pulse, and ships CI. This retires both of the
design's stated top risks: ADV bring-up, and the NimBLE 1.4.x-to-2.x port called "the largest
single unknown".

**The host side is ONE new component: a `shepherd` Herdr plugin** with its own
`herdr-plugin.toml` startup hook, which is simultaneously the Herdr client and the BLE central via
`bleak`. It speaks to Herdr through the CLI:

- `herdr agent list` returns, per agent, `agent_status`, `pane_id`, `workspace_id`, `cwd`,
  `terminal_title_stripped`, `state_change_seq`, `focused`. That is the frame content, already
  per-agent. Verified live on this host.
- `herdr agent read <target> --source detection` gives the blocking question text.
- `herdr agent send-keys <target> <keys>` sends the answer.

`walcew/herdr-assist` was dropped because (a) its one non-obvious asset, rule-based `agent_status`
derivation from terminal content, is dead weight on 0.8.2, (b) `herdr_bridge.py` binds
`BIND = os.environ.get("BRIDGE_BIND", "0.0.0.0")` on port 9375 with HMAC-signed UDP broadcast
discovery, which would have exposed agent input on five NLTG repos to the corporate LAN, and (c)
on Windows it only shells out to the CLI anyway (`USE_CLI = os.name == "nt"` selects `poll_loop()`
over `event_loop()`). Removing it also removed the localhost TCP hop, the token handling, the
second upstream, and the aggregate-to-per-agent translation layer.

Consequence: **the NVS namespace split no longer exists.** No WiFi anywhere, so NVS holds only BLE
bonds. Nothing to split, nothing to erase in the right order.

```
+- WORK LAPTOP -------------------------------------------+
|  Herdr server                                           |
|      |  named pipe (local IPC, no auth)                 |
|      |  agent list / agent read / agent send-keys       |
|      v                                                  |
|  shepherd  (own herdr-plugin.toml, startup hook)      |
|      . builds the per-agent frame directly              |
|      . label-matched dispatch + send-time re-verify     |
|      . bleak BLE central, chunk mtu_size-3, 10s keepalive|
+------+--------------------------------------------------+
       |  BLE 5 / NUS, Just Works LESC bond
       |  Nothing on the network. No port. No token.
+------v-------------------+
| Cardputer ADV            |
|  fork of y88huang build  |
|  queue-first UI (v1)     |
|  glance strip (v2)       |
+--------------------------+
```

### The action path was wrong, and is now the most-guarded part

**`send-keys y` does not approve a Claude Code prompt.** The permission prompt is a numbered
select list with a cursor glyph, the same widget visible in this host's live detection buffer. The
option set varies per prompt and across releases, and on some prompts an option is
"Yes, and don't ask again", which writes a persistent permission grant into a work repo's
settings. So neither `y` nor a fixed index is safe.

The dispatch path is therefore:

1. `k` is a closed set: `approve` | `deny` | `focus`. It indexes a hardcoded dict to a fixed argv
   list. `subprocess` with a list, never `shell=True`, never string interpolation.
2. `i` must match a `pane_id` from the most recent `agent list` or the action is discarded.
3. **Immediately before sending, re-read the pane and match the option by label text**, never by
   index, explicitly excluding any don't-ask-again or auto-mode option. Refuse to act if the
   expected label is not present.
4. **Compare the pane's current prompt against the text the device was shown.** Abort and
   re-notify on mismatch. Burn the decision id after use. `state_change_seq` proves snapshot
   freshness, not send-time freshness, and that is the difference between approving `git status`
   and approving whatever replaced it.
5. **Deny is always available; approve is refused when the prompt did not fit untruncated.** A
   truncated prompt renders as "open laptop". A 40-column display hides the dangerous tail of any
   real command.
6. **Every action appends to a local audit log**: timestamp, pane, full prompt text, keys sent,
   outcome.

### Wire protocol, final

Newline-delimited UTF-8 JSON over NUS; accumulate to a newline before decoding; chunk to
`mtu_size - 3` read after connect with a 20-byte floor, since WinRT cannot be asked for an MTU.

Kept: `v` protocol version, and the relay refuses a mismatched firmware with an on-screen message.
`hello` on connect carries `v` and `fw`.

**Dropped as dead code** on an ordered, ACKed link with one self-flashed device: `resync`, seq-gap
detection, and `n_extra`. Reconnect already triggers a full snapshot via `hello`.

**Changed:** `e` (elapsed seconds) becomes an absolute timestamp, so the device does no clock
arithmetic and cannot drift. Agent identity becomes a **stable 8-char alias per `pane_id`,
configured in the relay**, not a 22-char truncation, because `Yield_PriceManager_API` and
`Yield_InitialPricing_Service` do not survive truncation as distinct identities you are about to
approve against.

Question text is fetched once on transition into `blocked` and cached against that agent's
`state_change_seq`.

### Push policy

Push only when some agent's `state_change_seq` moves, or every 10s as keepalive. This is what
makes battery life achievable at all: a 1Hz push keeps the radio hot, and at a 23-byte MTU a
5-agent frame is 25-35 writes and roughly a second of airtime per push.

`herdr` CLI now, a named-pipe implementation later behind the same `HerdrSource` seam. Note the
naming rule verified on this host: `events.subscribe` takes the **dotted** form in
`params.subscriptions[].type`; `events.wait` and the emitted event's `type` const both use
**underscores**. Mixing them is a silent false negative.

### Device UX: queue first, strip second

v1 is a **one-prompt-at-a-time queue**: agent alias, full prompt text, approve / deny / next. This
keeps y88huang's inherited input model intact and reaches the acceptance test fastest. A second
prompt queues behind the first. The 3x glance strip in `## Approved Screen Layout` above becomes
v2 on the same wire protocol. The glance is the fun; the queue is the function.

### Failure states

On `herdr` CLI failure or timeout, the relay pushes an explicit frame marking every agent
`unknown` with a reason, rather than leaving the last good frame on screen. Device-side, no frame
for 30s against a 10s keepalive renders the unknown glyph. That rule fires even when the relay is
dead, which the host-side rule cannot.

### Testing

Seams on both sides from commit one: `herdr` behind a `HerdrSource` protocol and BLE behind a
`Transport` protocol, with pytest fakes covering all 26 relay code paths; the firmware frame
parser in its own translation unit with a PlatformIO `native` test env. Only two flows need
hardware. The coverage audit found 44 untested paths and no test infrastructure of any kind.

### Success criteria, reframed

This is a side project for fun and learning, and the earlier criteria were product-grade. They are
now **learning goals**: build a BLE peripheral, learn NimBLE and GATT, see the herd on the desk,
approve something real once. Battery life, reconnect time and full-working-day become
**observations to record, not gates**.

**One criterion remains non-negotiable:** the device never *acts* on state it has not re-verified.
Herdr's `blocked` is rule-derived from terminal scraping, so "the strip is never wrong" was never
achievable; bounded staleness plus send-time re-verification is the achievable version of the same
safety intent.

Also: `w2:p1` on this host is running auto mode and never prompts. Measure the real block rate
across all five repos before weekend one. If it is twice a day the device does not earn a pocket;
if it is forty times a day the permission config is the actual defect.

### Probe 1: BLE pairing policy — PASS

Caveats: absence today is not a guarantee, since Intune can push a Bluetooth CSP into exactly that
key at any time — if pairing later breaks mysteriously, check there first. And the
`DeviceInstall\Restrictions` key existing at all means device-installation policy *is* managed here,
just not as a deny list, so future tightening is plausible. Policy not blocking this is also not the
same as it being sanctioned: the audit log required above is the artifact that makes a personal BLE
peripheral on a managed endpoint defensible, and endpoint security should hear about it before the
device lives on the desk permanently.

### Probe 2: the approve keystroke — CAPTURED, and worse than predicted

Captured on **Claude Code v2.1.260** in a throwaway workspace, which was then closed.

**Two different widget shapes appeared in one session.** The startup trust gate:

```
 ❯ No, exit
   Yes, I trust this folder

 Enter to confirm · Esc to cancel
```

Unnumbered options, cursor defaulting to the **refusing** option. The Bash tool prompt:

```
 Bash command
 Tip: auto mode handles these prompts for you — choose "switch to auto mode" below

   git --version
   Check git version

 This command requires approval

 Do you want to proceed?
 ❯ 1. Yes
   2. Yes, and don’t ask again for: git *
   3. Yes, and switch to auto mode · auto mode handles these prompts for you
   4. No

 Esc to cancel · Tab to amend
```

Numbered options, cursor defaulting to **`1. Yes`**, and a different footer.

Consequences:

1. **Neither numbering nor default position is stable across prompt kinds.** Proven, not theorised.
   `Enter` on the default would exit the agent on one widget and approve on the other.
2. **Three of the four Bash options are "Yes" variants.** Option 2 writes a persistent `git *` glob
   permission. **Option 3 disables permission prompting entirely for that agent** — nobody predicted
   this one, and it is strictly worse than option 2: a device that selected index 3 would silently
   turn off the human-in-the-loop control it exists to serve.
3. **`Esc` is the one reliable key.** It cancels on both widget shapes. Verified end to end:
   `agent_status` went `blocked` → `done` and `state_change_seq` advanced 439 → 440. **Deny therefore
   needs no label matching at all** — only approve does.
4. Option 2 contains a typographic apostrophe (U+2019), so label matching must be Unicode-aware, and
   the Cardputer's ASCII-only font would mangle it.
5. The command text and its description sit on separate lines above the question. That is the text
   the device renders and re-verifies against.

**The approve predicate, final.** Strip the `❯ ` cursor and any `N. ` prefix, then select the option
whose label is **exactly `Yes` with nothing following it**. Reject any label beginning with `Yes,`
— one rule excludes both the glob grant and the auto-mode switch. Refuse to act if no such label is
present. Record the Claude Code version in the audit log, because the option set is version-specific.

### Incidental findings

- **A fresh agent with default settings came up in `⏵⏵ auto mode on`** and never prompts.
  `shift+tab` cycles to `⏸ manual mode on`. Combined with `w2:p1` already being in auto mode, this
  strengthens the case for measuring the real block rate before building: the device's core event may
  be rare by configuration.
- **Herdr's native `blocked` detection fired correctly on both widget shapes.**
- **`done` is not a synonym for `idle`.** Both are the same readiness state, distinguished by whether
  the tab has been seen in the focused UI — so `done` means *finished and you have not looked yet*.
  CLI reads do not mark a tab seen. For a glance device that is more actionable than `idle`, so

### Probe 3: socket surfaces — PASS

Exercised and behaving as assumed: `agent read --source detection`, `agent send-keys`,
`agent prompt --wait`, `workspace create` / `close`, `agent list`, `agent get`.

The named-pipe path is validated end to end **from stdlib Python, no pywin32**:

```python
open(r"\\.\pipe\C:\Users\<u>\AppData\Roaming\herdr\herdr.sock", "r+b", buffering=0)
```

Request envelope is `{"id", "method", "params"}`, newline-delimited. Errors return

### Probe 4: does the status event fire? — PASS, with an architectural catch

**It fires on 0.8.2.** Observed live, with this session's own pane as the trigger:

```
16:50:23  PUSHED  pane.agent_status_changed | wA:p1 | done
16:51:34  PUSHED  pane.agent_status_changed | wA:p1 | working
```

```json
{"event": "pane.agent_status_changed",
 "data": {"agent": "claude", "agent_status": "done",
          "pane_id": "wA:p1", "workspace_id": "wA"}}
```

herdr-assist's "0.8.0 does not emit it" is real but stale; `lfsmoura/led-agent-status` was right.

**There is a fourth naming surface, and the push channel is dotted.** Correcting the table at the
top of this document:

| Surface | Field | Spelling |
|---|---|---|
| `events.subscribe` | `params.subscriptions[].type` | **dotted** |
| `events.wait` | `params.match_event.event` | underscored |
| the `event` schema record | `type` const | underscored |
| **the push envelope** | `event` (alongside `data`) | **dotted** |

Only **three** kinds actually stream (`SubscriptionEventKind`): `pane.output_matched`,
`pane.agent_status_changed`, `pane.scroll_changed`.

**The catch, and it decides the architecture.** The subscription is **per-pane, not global**:

```json
"pane.agent_status_changed": {
  "required": ["type", "pane_id"],
  "properties": {"pane_id": {...}, "agent_status": {"...optional filter..."}}}
```

Three consequences:

1. The relay must enumerate panes before it can subscribe to anything, and re-subscribe whenever
   membership changes.
2. **New-agent discovery has no push path.** `pane.agent_detected` does not stream, so polling
   `agent list` is permanent, not a stopgap.
3. The optional `agent_status` filter means Herdr can push **only** transitions into `blocked` —
   exactly the event the device exists for, filtered at the source.

The push payload is also thin: `agent`, `agent_status`, `pane_id`, `workspace_id` and nothing else.
No `state_change_seq`, no `cwd`, no `terminal_title_stripped`. It tells you *which pane changed and
to what*, not enough to render a row.

### Revised: HerdrSource is poll-plus-push (supersedes the CLI-first decision)

The schema forces a hybrid, so the earlier "CLI now, named pipe later behind the seam" is void.
One `HerdrSource` does both:

- **`herdr agent list` every ~30s** for membership and display metadata (names, cwd), and to detect
  agents that appeared or vanished. Re-subscribe on any membership change.
- **One `pane.agent_status_changed` subscription per pane** over the named pipe, with
  `agent_status` filtered to `blocked`, for the transition that matters.

This drops CLI spawns from roughly 86,000 per working day to a few hundred, and makes the chirp
instant rather than poll-interval bound. The `HerdrSource` seam still stands — it is now one
implementation using two mechanisms rather than two implementations swapped over time.


## T24: measured block rate (2026-09-05)

The one thing the plan asserted without evidence: how often an agent actually blocks. Measured
rather than assumed, because the device's core event depends on it.

### Every agent is in auto mode

All five live agents report `⏵⏵ auto mode on`, and so did a freshly started agent with default
settings during probe 2. In auto mode a permission prompt appears only when the classifier declines
to auto-approve.

### There are no allowlists anywhere

`allowedTools: [0 items]` across **all 39 tracked projects** in `~/.claude.json`. No
`~/.claude/settings.json`, no `~/.claude/settings.local.json`, no managed settings at
`ProgramData`. A single stray `settings.local.json` in one repo.

This matters for how the strategic critique lands. The outside voice argued "if Shepherd chirps
40 times a day, your permission config is wrong". The config is not wrong — it is absent, and auto
mode is carrying the load. So there is no allowlist-tightening exercise that would make blocks
rarer; they are already rare.

### Historical rate, from the transcripts

Counting the canonical tool-rejection marker across 297MB of session transcripts in
`~/.claude/projects`:

| Metric | Value |
|---|---|
| Transcript span | 2026-08-11 → 2026-09-05 (25 days) |
| Sessions | 39 |
| Tool rejections | 16 total, ~14 organic (2 are this project's own probes) |
| Sessions with at least one rejection | 12 of 39 (31%) |
| Organic rejections per day | **~0.56** |

**Limit of the measurement:** this counts *denials*. An approved prompt leaves no distinguishable
trace in the transcript, so 14 is a lower bound on blocks rather than a count of them. But since a
prompt only appears in auto mode when the classifier declines, the true figure cannot be far above
it — single digits per day at the very most, and plausibly around one.

### Consequence: `done` is the real notification event

The pager fires rarely. The glance does not. `working` → `done` transitions happen constantly —
probe 4 captured two from a single agent inside a 90-second window.

Recall that `done` is not a synonym for `idle`: both are the same readiness state, distinguished by
whether the tab has been seen in the focused Herdr UI. So `done` means *finished, and you have not
looked yet*. On a herd of five agents that is the event with daily value, and blocks are the
dramatic exception rather than the routine case.

Two adjustments follow, neither of which reopens a decision:

1. **`done` earns the loudest glyph on the strip**, and is the state the chirp should fire on by
   default — with `blocked` louder still. The earlier framing treated `blocked` as the only event
   worth a sound.
2. **Queue-first (Issue 12) still stands** as build order, because it remains the fastest route to
   proving the device works end to end. But the strip is what will get used day to day, so it is a
   near-term follow-on rather than a someday v2.

This also sharpens what "the device earns its place" means: not "it caught a block from the sofa",
which will happen roughly once a day, but "I stopped alt-tabbing to find out which of five agents
had finished".
